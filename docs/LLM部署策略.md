# LLM 部署策略:競賽用雲端,落地改地端

## 立場

- **競賽階段用雲端模型 API。** 競賽只使用公開數據集與合成資料,沒有企業機密外送的問題(構想書第四節)。
- **實地部署時改為地端或私有環境。** 製造資料牽涉客戶 NDA 與營業秘密,落地時模型在廠內網路運行,生產資料不離開企業。
- **切換是改設定,不是改架構。** 與構想書「接上實廠是改設定」的原則一致。

## 為什麼切換成本低

FactoryMind 的分工讓模型的責任很窄:

| 工作 | 由誰做 |
| --- | --- |
| 交期、成本、負載、換模次數 | 求解器與虛擬工廠試跑 |
| 硬規則檢核、方案排序、授權判定 | 確定性程式 |
| 理解事件與主管提問、提出候選策略、撰寫摘要 | 語言模型 |

模型不產生數字,也不能放寬硬規則,所以換模型不會改變計算結果,只影響語意理解與文字品質。

實作上遵守三點:

1. 所有模型呼叫集中在單一模組,其他程式不直接碰供應商 SDK。
2. 模型位址、模型名稱、金鑰由環境變數決定,不寫死在程式裡。
3. 模型輸出一律要求結構化格式,經 schema 驗證後才進入流程;驗證失敗做有界重試,仍失敗就退回規則基準並明確標示(架構文件第 10 節)。

## 地端怎麼實行

1. **模型**:選用可商用授權的開放權重模型,依硬體選擇規模。
2. **推論服務**:在廠內 GPU 主機上以 vLLM 這類推論伺服器啟動,它提供與雲端相同形式的 HTTP 介面,並支援工具呼叫與結構化輸出。
3. **接入**:把 FactoryMind 的模型位址指向廠內主機,其餘程式不變。
4. **網路**:主機只開放給 FactoryMind 後端,不需對外連線。
5. **驗收**:用同一組測試情境分別跑雲端與地端模型,比較事件分類、候選策略格式正確率與回應時間,再決定是否上線。

## 地端與雲端的實作差距

| 面向 | 雲端 API | 地端 |
| --- | --- | --- |
| 資料 | 提示內容會送到外部服務 | 資料留在廠內 |
| 模型能力 | 最新大型模型,結構化輸出與工具呼叫穩定 | 受硬體限制,通常用較小的模型,格式錯誤率較高 |
| 回應速度 | 穩定,受網路影響 | 取決於 GPU 與同時請求數 |
| 成本 | 按用量計費,無前期投入 | 前期硬體投入,之後主要是電費與維運 |
| 維運 | 供應商負責 | 企業自行負責更新、監控與備援 |
| 版本 | 供應商可能更新或下架模型 | 版本自行固定,稽核時可重現 |

## 因應差距的設計

- **任務切小**:每次呼叫只做一件事(分類、抽取條件、提策略、寫摘要),小模型也能勝任。
- **格式由推論服務約束**:地端使用限定輸出格式的功能,降低格式錯誤。
- **規則基準後備**:模型不可用或輸出不合格時,事件偵測與候選方案仍可由規則產生。
- **記錄模型版本**:每筆決策紀錄保存模型名稱與版本,換模型後仍可追查。

## 現階段

底層(虛擬工廠、試跑、硬規則、排序)完全不呼叫模型,可先行開發與測試;模型於治理主線完成後再接入。
